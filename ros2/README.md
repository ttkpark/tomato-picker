# ros2/ — 새 계통: **무대를 외우지 않고 좌표로 딴다**

> 이 디렉터리는 기존 파이썬 스택(`src/tomato_picker/`)을 **대체하러** 온 것이 아니라,
> 그 스택이 구조적으로 풀 수 없는 문제 하나를 풀러 왔다. 기존 스택은 계속 돈다.
> 계통 분리와 태그 규칙은 [`docs/ros2-이행계획.md`](../docs/ros2-이행계획.md).

---

## 1. 왜 갈아엎는가 — 기존 스택이 못 푸는 문제

지금 로봇은 토마토를 **화면 좌표**로 안다.

```
카메라 픽셀 (x, y)  →  harvest.SceneModel이 "몇 번 나무, 위/아래"로 분류
                    →  arm.play_blended(y)가 저장해 둔 자세를 보간 재생
```

여기 어디에도 **미터가 없다.** 그래서 이런 일이 일어난다.

| 증상 | 진짜 원인 |
|---|---|
| 무대를 옮기면 열매 번호가 어긋난다 | 나무 위치를 **관측한 픽셀 x**로 배운다 (`~/harvest_scene.json`) |
| 서비스를 재시작하면 학습이 날아간다 | 무대가 **상태**다. 재학습 첫 프레임이 오검출이면 그게 무대가 된다 |
| 열매가 20cm 앞으로 오면 헛집는다 | 자세는 **저장된 관절값**이다. 거리를 모르니 보정할 수 없다 |
| 카메라를 조금 돌리면 전부 틀어진다 | 픽셀↔자세 대응이 **그 카메라 각도에 통째로 묶여** 있다 |

이건 튜닝으로 못 고친다. **"토마토가 어디 있는가"를 미터로 말할 수 없는 구조**라서 그렇다.

## 2. 새 계통이 세우는 계약

```
D405가 준 (u, v, depth)  ──내부파라미터──▶  카메라 좌표 3D (mm)
                          ──손-눈 변환 T_base_cam──▶  팔 base 좌표 3D (mm)
                          ──IK──▶  관절 각
```

무대 학습이 없다. 저장된 자세도 없다. **좌표 하나가 끝까지 간다.**
무대를 옮겨도, 카메라를 다시 달아도, 열매가 처음 보는 자리에 있어도 같은 식이 돈다 —
단, **손-눈 변환을 다시 재야 한다**(카메라를 옮겼을 때만. 무대는 상관없다).

> 이게 "일반적인 환경에서도 변함없이"의 조작적 정의다. 무대에 대한 가정을
> **하나도 안 하는 것**이지, 무대를 더 잘 배우는 게 아니다.

## 3. 왜 ROS인가 — 세 가지, 그 이상은 아니다

ROS를 쓰는 이유는 "표준이니까"가 아니다. 위 계약을 **혼자 구현하면 반드시 틀리는**
부분이 셋 있어서다.

1. **TF** — 좌표계가 다섯 개(`base_link`, `arm_base`, 관절 5개, `tool0`, 카메라)를 넘어가면
   변환 합성과 **시각 정렬**(그 프레임을 찍은 순간의 팔 자세)을 사람이 손으로 못 맞춘다.
   기존 스택에서 `line_drive.py`가 겪은 부호 사고들이 전부 이 문제의 축소판이다.
2. **시간** — 깊이 프레임과 관절값은 **다른 시각**의 데이터다. 팔이 움직이는 중에 찍은
   프레임을 지금 관절값으로 풀면 그만큼 틀린다. `tf2`의 시간 보간이 이걸 공짜로 준다.
3. **교체 가능성** — 검출기를 HSV→YOLO로, 카메라를 D405→다른 것으로 바꿔도
   토픽 타입이 같으면 나머지가 안 바뀐다. [`docs/보드-계약.md`](../docs/보드-계약.md)가
   주행 보드에 대해 세운 원칙과 **같은 원칙**을 인식·팔에 적용하는 것이다.

ROS가 **안 하는 것**도 적어 둔다: 정지마찰 문턱을 없애 주지 않고, 영점을 대신 잡아
주지 않고, 잘못 잰 링크 길이를 고쳐 주지 않는다. 그건 여전히 우리 몫이다.

## 4. 단위 경계 — 어디서 무엇이 바뀌는가

이 프로젝트에는 이미 단위가 셋 있고, 섞이면 그 자리가 곧 버그다.

| 구간 | 단위 | 근거 |
|---|---|---|
| ROS 토픽·TF·URDF | **m, rad** | REP-103. 여기만은 타협 없음(모든 표준 노드가 이걸 가정) |
| 기구학·손눈보정 (`kinematics.py`, `handeye.py`) | **mm, °** | 기존 자산. 링크 길이를 자로 재서 넣는 곳이라 mm가 맞다 |
| 주행 보드 시리얼 | **mm/s, mdeg/s** | [`docs/보드-계약.md`](../docs/보드-계약.md) §2① |

변환은 **경계 노드 안에서 한 번만** 한다. 노드 내부에서 두 단위를 같이 쓰지 않는다.
경계는 정확히 세 곳이다 — `joint_state_node`(° → rad), `cmd_vel_node`(m/s → mm/s),
`handeye_node`(mm → m).

## 5. 구성

```
ros2/
├─ docker/            젯슨에서 도는 방법 (L4T 커널 위 Jazzy 컨테이너)
├─ src/
│  ├─ tomato_msgs         Fruit3D / FruitArray / 보정 서비스
│  ├─ tomato_description  URDF(xacro) — kinematics.py와 **같은 링크 길이**
│  ├─ tomato_bridge       기존 하드웨어를 ROS에 물리는 다리 (팔 관절 / cmd_vel)
│  ├─ tomato_perception   D405 → 열매 3D 점 (팔 좌표계로 변환해서 발행)
│  ├─ tomato_handeye      손-눈 보정 수집·풀이·static TF 발행
│  └─ tomato_bringup      런치와 파라미터
└─ tools/ros_selfcheck.py  **ROS 없이 PC에서 도는 검증** (아래)
```

### 왜 `ros_selfcheck.py`가 있는가

이 저장소의 규칙이다 — [`kinematics.py`](../src/tomato_picker/hardware/kinematics.py)가
`import math` 하나로 버티는 이유, [`handeye.py`](../src/tomato_picker/hardware/handeye.py)가
numpy 하나로 버티는 이유와 같다. **숫자가 맞는지를 확인하려고 매번 젯슨에 올려 팔을
흔들 수는 없다.** 그래서 각 패키지의 계산 부분은 `rclpy`를 import하지 않는 순수 모듈로
떼어 놓고, PC에서 이걸 돌린다.

```bash
python ros2/tools/ros_selfcheck.py        # ROS도 젯슨도 필요 없음
```

`rclpy`가 들어간 파일은 `*_node.py` **뿐이다.** 그 규칙을 셀프체크가 직접 검사한다.

## 7. ⚠ 기존 스택과 **동시에 켜지 말 것**

포트는 한 프로세스만 연다(`exclusive=True`). 팔(`/dev/ttyACM0`)과 주행 보드
(`/dev/ttyUSB0`) 둘 다 그렇다.

```bash
sudo systemctl stop tomato-voice controller-drive     # 먼저 비운다
```

비우기 싫다면 `tomato_bridge`를 **proxy 모드**로 띄운다 — 기존 대시보드의
`GET /status` / `POST /cmd`를 통해 팔을 읽고 움직이므로 포트를 안 잡는다.
느리지만(폴링 ~10Hz) 데모 중에 나란히 띄워 볼 수 있다. `ros2/docker/README.md` 참고.
