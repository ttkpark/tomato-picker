# 개발 노트 — 2026-08-09

하루 동안 **모터 소음/끊김 → 프리셋·리더암 → 바닥 카메라 라인 주행 → 팔 재캘리브레이션**까지
갔고, 마지막에 **±1cm 편차에서도 토마토 파지 성공**을 확인했다.

이 문서는 "무엇을 만들었나"가 아니라 **"무엇에 속았고 어떻게 알아챘나"** 를 남긴다.
코드가 무엇을 하는지는 각 파일 docstring이 설명한다. 여기 있는 건 그 코드를 그렇게 쓰게
만든 **증상 → 오진 → 진짜 원인** 의 기록이다.

## 1. 이번에 가장 크게 배운 것 세 가지

### ① 증상이 가리키는 곳과 원인이 있는 곳은 다르다

| 증상 | 처음 의심한 곳 | 진짜 원인 |
|---|---|---|
| 주행 중 "우우웅" | 통신(시리얼) | **PWM 50Hz** — 가청 대역 |
| 라인이 안 잡힘 | 검출 알고리즘 | **카메라 색 캐스트** — 절대 임계가 무의미해짐 |
| yaw가 발산 | 보정 **부호** | **각도 측정 자체가 쓰레기값** |
| 바퀴가 안 움직임 | 시리얼 끊김 | 보드가 **USB는 붙은 채로 조용히 사망** |
| 리더암이 제멋대로 움직임 | 미러링 버그 | **리더를 팔로워로 열었음**(포트 식별 실패) |

부호를 뒤집는 것처럼 **"둘 중 하나"인 문제는 두 번 시도하면 끝난다.** 두 번 다 실패하면
그건 부호 문제가 아니다 — 측정이 잘못됐거나 모델이 틀린 것이다. yaw에서 이걸 놓쳐서
부호를 두 번 뒤집는 동안 원인(2점 표본 각도 추정)을 못 봤다.

### ② 절대 임계값은 현장에서 반드시 무너진다

세 번 같은 방식으로 당했다.

- 밝기 절대 임계 → 마루 나뭇결을 갈라 **유령 라인** 생성
- `score = V-2S` 절대 임계 90 → 색 캐스트에서 **통과 픽셀 0%**
- 채도 절대 임계 90 → 캐스트에서 **검은 테이프가 가장 채도 높은 물체**가 됨

해법은 항상 같았다: **프레임 자기 통계 기준**(중앙값 대비 여유폭 + 백분위) + **물리적
성질 검사**(폭·두께·면적·밝기). "이 장면에서 가장 밝고 무채색인 것"은 조명이 바뀌어도
테이프를 가리키지만, "밝기 90 이상"은 조명이 바뀌면 아무것도 못 가리킨다.

### ③ 원격에서 확정 못 하는 값은 코드에 박으면 안 된다

축·부호·주파수·기준선처럼 **실물을 손으로 밀어봐야 아는 값**을 코드 상수로 두면
한 번 확인할 때마다 배포 왕복이 필요하다. 전부 이렇게 바꿨다:

1. 대시보드에서 즉시 바꾸고
2. 파일에 저장해 재시작해도 유지하고 (`~/line_tuning.json`, `~/base_tuning.json`, `/dev/shm/line_target_y`)
3. **정지 중에도 "지금이라면 이렇게 보낸다"를 표시**해 움직이기 전에 검증

3번이 특히 중요했다. 부호가 맞는지 확인하려고 로봇을 굴려볼 필요가 없어진다.

## 2. 모터 · 펌웨어

### PWM 주파수가 소음의 정체

벤더 코드가 `set_hz(50)`이었다. 50Hz는 사람이 그대로 듣는 대역이라 모터가 초당 50번
끊기며 도는 게 "우우웅"으로 들린다. **PCA9685의 물리적 상한은 1526Hz**(prescale=3)라
초음파로 도망갈 수 없다 — "무음"은 선택지가 아니고 저역 울림과 고역 휘파람 중 고르는 것.

그리고 **주파수를 올리면 속도가 떨어진다.** 드라이버 스위칭 손실 때문. 보상은 듀티로
한다 — 벤더 코드도 `MAX_VALUE=2000`(4095 중 49%)만 써서 **2배 헤드룸**이 남아 있었다.

정착값: **700Hz · 듀티 2600**. 실측 비교:

| 주파수 | 소리 | 힘 |
|---|---|---|
| 50Hz | "우우웅" 저역 | 가장 셈 |
| 700Hz | 웅~찡 경계 | 중간 (채택) |
| 1526Hz | "찌잉" 고역 | 가장 약함 |

### ⚠ 포트를 열면 Uno가 리셋된다 (가장 오래 헤맨 함정)

`dtr=False`로 열어도 **커널이 포트 open 시 DTR을 순간 토글**해 Uno가 리셋된다.
직후 ~2초는 부트로더 구간이라 **이때 보낸 설정(F/P/R)은 통째로 먹히고 응답도 없다.**

- 증상: 설정한 대로 안 도는데 **에러도 안 남**
- 판별: 보드의 `rx=` 카운터가 **0부터 다시 시작**
- 해법: **첫 하트비트를 받은 뒤** 설정을 밀어넣는다(blind sleep 대신 이벤트)
- 검증: 대시보드에 보드의 `ok F 700 | ok P 2600` 확인 응답을 그대로 노출

"보냈다"와 "먹혔다"는 다르다. **확인 응답을 화면에 띄우는 것**이 유일한 증거다.

### 보드는 USB가 붙은 채로도 조용히 죽는다

`ch341 disconnect` 로그도 write 예외도 없이 보드만 멈췄고, 젯슨은 **14분 동안 아무도
안 듣는 포트에 지령을 써 넣고** 있었다. 대시보드엔 "연결됨"이 떠 있었다.

유일한 단서가 `hb_age`(하트비트 나이)였다. → 진단은 **항상 hb_age부터**. 지금은 5초
침묵 시 포트를 다시 열어(=DTR로 리셋) 스스로 살아나고, 복구 횟수를 화면에 띄운다.
**그 숫자가 0이 아니면 워치독이 증상을 덮고 있는 것** — 전원/배선을 의심할 것.

### 그 외

- **포트는 한 프로세스만** (`exclusive=True`). `tomato-voice`와 `controller-drive`를 동시에
  켜면 나중 쪽이 busy로 실패한다. 예전엔 짧게 열고 닫아서 우연히 굴러갔다.
- **가감속(슬루)은 펌웨어가** 해야 한다. 파이썬이 램프를 만들면 지연·지터가 그대로
  전류 스파이크가 되지만, 5ms 틱을 도는 AVR이 하면 매끄럽다.
- **`V`에 응답하지 말 것.** 50Hz로 들어오는 지령마다 `ok`를 되쏘면 TX 버퍼가 차서
  loop가 막힌다. 상태는 1초 하트비트에 실어 보낸다.
- 펌웨어 v1/v2 구분법: 지령에 `ok V ...`를 되쏘면 v1, 조용하면 v2. **겉보기 주행은 둘 다 된다.**

## 3. 비전 (바닥 카메라 / 라인)

### 코스 기하를 90° 잘못 잡았다

통상적 라인트레이서(검은 세로선을 따라 조향)를 가정하고 만들었는데, 실제 코스는
**테이프가 진행 방향과 나란히** 깔려 있었다. 바닥 카메라에는 **가로 띠**로 보인다.

    띠의 세로 위치 = 테이프까지의 거리   →  게걸음(vy)
    띠의 기울기   = 로봇 요(yaw) 오차    →  회전(w)
    화면 가로     = 진행 방향            →  전후(vx)

**교훈**: 화면의 축과 로봇의 축을 대응시킬 때 추측하지 말 것. 사용자가 "vx로는 테이프
거리를 구할 수 없다"고 한 마디로 정리해줬는데, 그게 정답이었다. 스크린샷 한 장이
내 전제를 무너뜨렸다 — **실물 사진을 일찍 봤어야 했다.**

### 색 캐스트가 모든 절대 임계를 무너뜨린다

카메라 AWB가 흔들려 화면이 보라빛으로 물들자:

| | score 중앙값 | 테이프 | 절대임계 90 통과 |
|---|---|---|---|
| 중립 | 66 | 124 | 16.4% → 정상 |
| 보라 캐스트 | 7 | 58 | **0.0% → 전멸** |

그리고 **검은 테이프의 채도가 프레임 최고(113)로 올라가** 색 마커로 오인됐다.
어두운 물체가 캐스트를 받으면 채도가 치솟는다 — **채도로 검정을 판별하면 안 된다.**

`wbmode` 고정은 답이 아니었다(실측: auto 33.9 / daylight 59.8 / incandescent 73.5 —
프리셋 고정이 오히려 악화). 소프트웨어에서 상대 기준으로 가는 게 맞았다.

### 각도 추정: 표본 2개는 되먹임 루프에 넣으면 안 된다

좌/우 1/3의 무게중심 **두 점**으로 기울기를 계산했다. 잡음이 그대로 각도로 증폭되고,
그 구역에 띠가 아닌 밝은 것(흰 무대·반사·케이블)이 들어오면 중심이 통째로 끌려갔다.
로봇이 움직이면 그것들이 시야에 들락날락하니 각도가 **자세와 무관하게** 튀었다.

→ **띠 행 범위 안에서만** 열별 중심을 구해 최소자승 직선을 맞춘다(표본 수백 개).
검증: 기대 ±5.4°에 측정 ±5.2°, 흰 방해물을 넣어도 0.0°.

### 시각 오도메트리가 잘 먹힌다

바퀴 엔코더 없이 변위를 알아야 했다. `cv2.phaseCorrelate`로 연속 프레임의 바닥 무늬
이동량을 재면 **슬립·배터리 전압과 무관한 실제 이동거리**가 나온다. 실기 신뢰도 0.79~0.82.
저속일수록 정확하다(모션블러가 적어서) — 느리게 가는 게 오히려 유리한 드문 경우.

누적값은 흐르므로 **양끝 검은 테이프에서 원점을 다시 잡아** 오차를 턴다.

## 4. 제어

### 펄스 주행이 연속 저속을 이긴다

저속으로 계속 밀면 바퀴가 정지마찰을 겨우 넘나들며 **붙었다 풀렸다** 하다가 갑자기
쭉 미끄러진다. 짧고 빠른 펄스를 반복하면 **한 걸음 거리가 일정**해져 예측 가능해진다.

별도 모드로 만들지 않고 **같은 설정의 양 끝**으로 융합했다 — `ON == 주기`면 연속 주행.
슬라이더 하나로 오간다. 모드 스위치는 상태를 늘리고 사용자를 헷갈리게 한다.

### 안전은 "폭주 방지"가 아니라 "모르면 정지"

부호가 반대일 수 있는 되먹임 루프를 사람 앞에서 돌린다는 전제로:

- 테이프 분실 0.4초 → 정지 (눈 감고 달리지 않는다)
- 기준선 과이탈 → 정지 (부호가 반대여도 폭주 대신 멈춤)
- 명령 타임아웃 25초
- 수동 조작이 들어오면 자동주행 취소
- 상위 루프가 죽어도 MotorLink 0.5초 + 펌웨어 데드맨

### 출발 전 점검이 "눌렀는데 바로 멈춤"을 없앤다

기준선이 어긋난 상태에서 주행 버튼을 누르면 출발하자마자 안전정지에 걸렸다. 사용자
눈에는 "버튼이 안 먹는다"로 보인다. → **출발 자체를 거부하고 무엇을 눌러야 하는지**
메시지에 담는다. 실패는 조용하면 안 되고, 실패 메시지는 다음 행동을 지시해야 한다.

## 5. 로봇 팔

### ⚠ 리더/팔로워는 USB 시리얼번호로만 구분된다 (실사고)

둘 다 같은 CH343(`1a86:55d3`, product `USB Single Serial`)이라 **VID:PID도 product
문자열도 같고 ttyACM 번호는 꽂는 순서마다 바뀐다.** "이름에 `USB_Single_Serial`이
들어간 첫 by-id"를 팔로워로 삼았더니, 리더만 꽂힌 채 서비스가 뜬 날 **리더암이
팔로워로 열려 토마토 따는 프리셋을 재생**했다.

→ 시리얼번호로 못 박고, 못 찾으면 **폴백하지 않고 명확히 실패**한다.
(팔로워 `5AE6055389` / 리더 `5AE6083531`)

### 프리셋은 캘리브레이션 상대값이다

`arm_presets.json`의 `.pos`는 각도가 아니라 **정규화값**이라, 범위를 다시 잡으면 같은
숫자가 다른 자세를 가리킨다. 교시한 슬롯 0~9가 통째로 어긋난다.

`tools/remap_presets.py`가 옛 캘리브레이션으로 숫자를 절대 엔코더 위치로 되돌린 뒤
새 기준으로 다시 적어 **물리 자세를 유지**시킨다(항등변환 오차 0.004, 왕복 0.011).

### 대화형 CLI는 웹으로 옮길 수 있다

`lerobot-calibrate`는 터미널에서 ENTER를 기다리는 대화형이라 원격에서 못 돌린다.
`SOFollower.calibrate`의 절차를 이벤트 기반으로 다시 구현해 대시보드에 붙였다.
안전장치: 폭이 100틱 미만인 관절이 있으면 **저장을 거부**한다(안 움직인 관절을
그대로 저장하면 그 축이 통째로 죽는다).

## 6. 시스템 · 배포

- **펌웨어와 파이썬은 둘 다 배포해야 한다.** 펌웨어만 굽고 파이썬을 안 올려서
  "부드러워졌는데 화면이 없다"가 났다. 반대도 마찬가지 — 한쪽만 올리면 증상이 섞여
  진단이 꼬인다.
- **`/dev/video*` 인덱스는 믿지 말 것.** CSI 카메라를 추가하자 `video0`을 CSI가 차지해
  무대 비전 서비스가 **CSI를 선점**하고 Argus 전체를 마비시켰다(`Failed to create
  CaptureSession`). `/dev/v4l/by-id/`로 열고, 못 찾으면 **인덱스 폴백 없이 실패**한다.
  조용히 엉뚱한 장치를 잡는 것보다 명확히 죽는 게 낫다.
- **vision venv의 OpenCV는 GStreamer 미지원**(`cv2.getBuildInformation()` 확인).
  `nvarguscamerasrc`를 직접 못 열어서, gst가 `/dev/shm`에 JPEG를 쓰고 파이썬이 읽는
  릴레이 패턴을 썼다(기존 tomato_vision과 같은 구조). 지연은 한 프레임 수준.
- **현장에서 고른 값은 파일에 남긴다.** 코드 상수로 두면 서비스가 재시작될 때마다
  조용히 기본값으로 돌아가서, 사용자가 매번 다시 누르게 된다.
- 젯슨엔 arduino-cli도 FaBo 라이브러리도 없다 → PC에서 `.hex`를 만들어 scp,
  젯슨에서 avrdude. **반드시 `systemctl stop tomato-voice` 먼저**(포트 독점).

## 7. 일반화된 설계 원칙

### 기계를 정밀하게 만들지 말고, 대상물을 지그로 물려라

오픈루프 메카넘의 정지 오차는 ±2cm다. 1mm를 요구하는 설계는 어떤 모터로 바꿔도
성립하지 않는다(엔코더를 달아도 메카넘은 슬립 때문에 mm급이 안 된다).

대신 **테이프를 기준(datum)으로 삼고 화분을 그 기준에 맞춰 옮기면** 오차 사슬의
마지막 고리가 0이 된다. 사용자가 스스로 도달한 결론이고, 산업 데모 셀이 실제로
이렇게 한다.

**역순 교시**: "토마토가 여기 있으니 팔을 맞추자"가 아니라 **"팔이 여기로 가니
토마토를 거기 두자"**. 로봇을 스테이션에 세우고 → 집기 프리셋을 재생하고 →
그 상태에서 화분을 밀어 맞추고 → 바닥에 윤곽을 그려 고정.

같은 논리가 색 마커 위치에도 적용된다. 카메라와 팔 사이 오프셋을 자로 재지 말고,
**팔이 정확히 닿는 위치에 로봇을 세운 뒤 그때 카메라가 보는 바닥에 마커를 붙이면**
오프셋이 자동으로 반영된다.

### 오차를 줄이려 하지 말고 흡수하는 사슬을 만들어라

1. **기계적 도킹** — 단 모서리에 밀착시키면 깊이와 요가 동시에 정렬 (±2cm → ±3mm)
2. **케이지에 정렬** — V홈 끼움으로 팔을 케이지 철사에 물리면 베이스 오차와 무관해짐
3. **탄성 줄기** — 짧은 범프는 흡수하고 지속적 당김만 자석에 전달 (실리콘 튜브 권장,
   찰흙은 크리프 때문에 부적합)
4. **그리퍼 스펀지 패드** — 셀프센터링 + 마찰 증가로 마지막 ±1.5cm 흡수

**결과: ±1cm 편차에서 파지 성공(2026-08-09).**

### 자석 딜레마 — 방향으로 풀어라

접근 시 살짝 닿으면 열매가 떨어지고(자석이 약함), 운반 시 그립에서 밀린다(자석이 강함).
같은 축의 양 끝이라 두께로는 못 푼다. **자석은 수직 당김에 강하고 전단/벗기기에 약하다** —
범프는 강한 방향으로 받고 추출은 약한 방향(아래로 벗기기)으로 하도록 배치하면 둘 다 풀린다.

## 8. 진단 순서 치트시트

**바퀴가 안 움직인다**
1. `/control` 링크 카드의 **`hb_age`** — 3초 넘으면 보드가 죽은 것
2. `수신` 카운터가 늘어나는지 — 안 늘면 지령이 안 닿는 것
3. `⚠ 링크복구 N회`가 0이 아니면 전원/배선 의심
4. `Device or resource busy` → `controller-drive`가 포트를 잡고 있음

**소리가 이상하다**
- 저역 "우우웅" → PWM 주파수가 낮음 (`/settings` 모터 튜닝)
- 고역 "찌잉" → 주파수가 높음. 속도가 같이 떨어졌으면 듀티로 보상

**라인을 못 잡는다**
1. 오버레이의 `contrast`/`separation` 수치 — 임계 미달이면 조명/테이프 문제
2. 화면에 흰 무대·반사가 크게 들어왔는지 (띠보다 큰 밝은 덩어리)
3. `band_y`가 튀면 각도 추정이 아니라 띠 검출부터 의심

**설정이 안 먹는다**
- 보드 확인 응답(`ok F ...`)이 화면에 뜨는지 — 없으면 부트로더가 먹은 것
- 파일에 저장됐는지 (`~/line_tuning.json`, `~/base_tuning.json`)
- 브라우저 캐시 — 배포 후에는 Ctrl+F5

**팔이 이상하게 움직인다**
- 어느 팔이 열렸는지 확인: `ls -l /dev/serial/by-id/` + 시리얼번호 대조
- 프리셋 숫자가 이상하면 캘리브레이션이 바뀐 것 → `remap_presets.py`

## 9. 남은 과제

- **배경색 통제 후 색 마커 켜기** (`LF_COLOR=1`) — 도화지를 깔면 hue가 안정될 것
- **회전 보정 켜보기** — 각 추정을 고쳤으니 `/settings`에서 켜서 확인. 안 켜도 메카넘은
  게걸음 보정만으로 게처럼 따라간다
- **진행 방향 부호 확인** — `오른쪽 끝까지`가 실제로 오른쪽인지(아니면 `[진행 좌우 ±]`)
- **끝단 왕복으로 변위 기준 잡기** — 양끝을 한 번씩 지나면 코스 길이가 잡혀 `%` 표시
- **전원** — 브라운아웃은 여전히 근본 미해결([[battery-power-system]]). 듀티를 키운
  만큼 전류도 커졌으니 젯슨이 리셋되면 듀티부터 되돌릴 것
- **젯슨 프리셋 백업** — 재캘리브레이션 후 다시 교시한 슬롯이 아직 저장소에 안 들어왔다
  (2026-08-09 세션 종료 시점에 젯슨이 응답 없음). 다음 접속 때 `~/arm_presets.json`을
  끌어와 `deploy/arm_presets.snapshot.json` 갱신할 것
