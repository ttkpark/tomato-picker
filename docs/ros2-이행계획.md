# ROS 2 계통 이행 계획 — 단계 · 브랜치 · 태그

> 새 계통이 **왜** 필요한지는 [`ros2/README.md`](../ros2/README.md)에 있다.
> 이 문서는 **언제 무엇을 하고, 어디에 이름을 붙이는가**를 정한다.
>
> 시작: 2026-08-28 · 브랜치 `feat/ros2-arm-estimation`

---

## 1. 두 계통은 나란히 산다

```
master ──● v1.0.0 ─────────────────────────────▶   기존 스택 (데모가 도는 쪽)
          \
           ●── v2.0.0-ros.1 ── ros.2 ── ros.3 ──▶   ROS 계통 (만드는 쪽)
```

**기존 스택을 지우지 않는다.** 이유는 감상이 아니라 일정이다 — 부스 데모는 지금
도는 것으로 하고, 새 계통은 옆에서 자란다. 둘이 같은 하드웨어를 쓰므로 동시에
켤 수는 없지만(포트는 한 프로세스만), `systemctl stop` 한 줄로 오간다.

새 계통이 기존 스택의 **모든 기능을 대체하면** 그때 `v2.0.0`을 달고 master를
옮긴다. 그 전까지 master는 언제나 "지금 데모에서 도는 것"이다.

## 2. 태그 규칙 — 계통이 태그 문자열에서 드러나야 한다

SemVer 하나로 통일하되, 새 계통은 **프리릴리스 라벨**로 갈라 둔다.

| 계통 | 형식 | 예 | 다는 곳 |
|---|---|---|---|
| 기존 스택 | `v1.MINOR.PATCH` | `v1.0.0`, `v1.1.0` | `master` |
| ROS 계통 | `v2.0.0-ros.N` | `v2.0.0-ros.1` | `feat/ros2-*` |
| 대체 완료 | `v2.0.0` | | master (그때) |

**왜 접두사(`ros/v0.1`)가 아니라 프리릴리스인가** — 순서가 자동으로 맞기 때문이다.
SemVer 우선순위에서 `1.0.0 < 2.0.0-ros.1 < 2.0.0`이므로, 도구가 정렬하든 사람이
읽든 "새 계통은 v2를 향해 가는 중"이 한눈에 보인다. 접두사로 나누면 두 계열의
선후관계를 사람이 외워야 한다.

```bash
git tag -l 'v1.*'            # 기존 계통만
git tag -l 'v2.0.0-ros.*'    # ROS 계통만
git describe --tags --match 'v2.0.0-ros.*'    # 지금 어느 이정표 뒤에 있나
tools/tag.sh v2.0.0-ros.2 "손-눈 보정 실측 통과"
```

**규칙 셋**

1. **계통을 섞어 달지 않는다.** ROS 브랜치에 `v1.x`를 달지 않고, master에
   `-ros.N`을 달지 않는다. 태그는 그 커밋이 **어느 계통의 이정표인지**를 말한다.
2. **이정표에만 단다.** 커밋마다 달지 않는다. 아래 §3의 표가 곧 태그 목록이다.
3. **되돌릴 수 없다고 생각하고 단다.** 태그를 밀어 놓고 옮기면(force) 남의 클론이
   조용히 다른 것을 가리킨다. 잘못 달았으면 지우지 말고 다음 번호를 단다.

## 3. 단계 — 각 단계는 **혼자서도 쓸모가 있다**

[`docs/보드-계약.md`](보드-계약.md) §13과 같은 원칙이다. 한 단계가 끝나면 그
상태로 멈춰도 손해가 아니어야 한다.

| 태그 | 무엇이 되는가 | 어떻게 확인하는가 |
|---|---|---|
| `v2.0.0-ros.1` | **골격.** URDF/TF, 팔·주행 브리지, D405 검출, 손눈보정, 자체검증 | `ros2/tools/ros_selfcheck.py` 전부 통과 · rviz에 팔이 실제 자세로 뜬다 |
| `v2.0.0-ros.2` | **실측.** 링크 길이·마운트를 자로 재고, 손눈보정 잔차 ≤15mm, 좌표로 보내면 집게가 거기로 간다 | 임의의 자리에 둔 열매를 `/arm/move_to_point`로 5회 중 5회 스탠드오프까지 도달 |
| `v2.0.0-ros.3` | **2단계 — 시각 서보잉.** 마지막 몇 mm를 눈으로 닫는다 | 링크 길이를 일부러 5% 틀리게 해도 집힌다 |
| `v2.0.0-ros.4` | **3단계 — MoveIt.** 충돌 회피·궤적 | 줄기 사이로 들어가 집는다 |
| `v2.0.0` | 기존 스택 대체 | 음성·대시보드·라인주행이 ROS 위에서 돈다 |

### 1단계 (`ros.1`) — 지금 여기

| | 상태 |
|---|---|
| URDF(xacro) + robot_state_publisher | ✅ |
| `/joint_states` (proxy/direct 두 길) | ✅ |
| `/cmd_vel` → 보드 (`C` 계약 + `V` 레거시) | ✅ (duty 곡선은 미실측) |
| D405 → `/fruits` (3D, 못 믿을 깊이는 **거절**) | ✅ |
| 손-눈 보정 (수집·풀이·static TF·잔차) | ✅ |
| `/arm/move_to_point` (TF → IK → 이동) | ✅ |
| ROS 없이 도는 자체검증 | ✅ `ros2/tools/ros_selfcheck.py` (69종, PC에서) |
| 손눈보정 수학 자체검증 | ✅ `tools/handeye_check.py` (45종, PC에서) |
| **젯슨에서 실제 빌드** | ✅ 2026-08-28 — 도커 이미지 3.02GB, `colcon build` 6패키지 1분 12초 |
| **로봇 위에서 TF 확인** | ✅ `bringup_check.sh` 0~2단 — RSP가 만든 TF가 `kinematics.forward()`와 **0.000mm** 일치 (7자세) |
| **실물 팔 직결 확인** | ✅ `arm_check.sh` 3~4단 — ROS가 포트를 직접 잡고 실물 관절을 읽는다. 그 TF가 **레거시 대시보드가 보고한 집게 좌표와 0.03mm 일치** |
| **카메라·검출 확인** | ✅ `cam_check.sh` 5~6단 — D405 컬러 27fps/깊이 26.7fps, 정렬 848x480 16UC1, `/fruits` 26.5Hz 발행 (팔 없이 돈다) |

**1단계에서 일부러 안 한 것들**

- *`C`(물리 단위) 전송* — 계산·검증은 다 돼 있지만 보낼 링크가 없다.
  `MotorLink`의 재전송 스레드가 `V`를 되풀이하므로 `C`와 섞으면 서로를 지운다
  (보드계약 §5.1). 물리 단위 보드가 생기면 계약 v2 전용 링크를 만들어 물린다.
  그때까지는 **거절**한다 — 조용히 duty로 내려가지 않는다.
- *오도메트리(`/odom`)* — 엔코더가 없다. 없는 것을 0으로 발행하면 "안 움직인다"가
  아니라 **"움직이지 않았다는 거짓말"**이 된다. 보드계약의 `enc`가 1이 되면 그때.
- *집게 관절값 읽기* — 대시보드 status가 안 준다. URDF에는 있으므로 0으로 채우고,
  파라미터 이름(`gripper_deg`)으로 "모른다"는 사실을 남겼다.

### 2단계 (`ros.3`) — 시각 서보잉

1단계가 끝나도 남는 오차가 있다. **링크 길이·영점·손눈보정의 오차가 전부 더해져
집게 끝에 나타난다.** 각각 몇 mm씩이어도 합치면 열매 반지름(15~20mm)을 넘는다.

그래서 2단계는 **열려 있는 사슬을 닫는다**:

```
집게에 붙은 마커를 카메라가 본다  →  "지금 집게가 실제로 여기 있다"
목표(열매)와의 차이를 계산        →  그 차이만큼만 조그
                                     (기구학의 절대 정확도가 필요 없어진다)
```

- 필요한 것: 집게 마커(1단계의 보정용 마커를 그대로 쓴다), 오차→조그 변환,
  수렴 판정, **발산 감지**(이 저장소에서 흔들기가 발산한 전례가 있다 —
  [개발노트 2026-08-09](개발노트-2026-08-09.md)).
- ⚠ 조그 크기가 서보 분해능(0.088°/틱) 아래면 물리적으로 0이다. `cartesian.py`가
  이미 그 크기를 거절하므로, 서보잉 루프는 **거절을 수렴 실패로 오해하면 안 된다**
  (거절 = "더 못 줄인다" = 수렴 종료).

### 3단계 (`ros.4`) — URDF + MoveIt

- `ros2_control` 하드웨어 인터페이스로 팔을 감싼다(지금은 서비스 호출).
- MoveIt2 설정 + 줄기·지지대를 충돌 객체로.
- ⚠ **5축이라 6자유도 목표는 못 푼다.** MoveIt에 6D 목표를 주면 계속 실패한다 —
  위치 + 접근 방향만 구속하는 방식으로 목표를 세워야 한다
  ([`kinematics.py`](../src/tomato_picker/hardware/kinematics.py) 머리말 참고).

## 4. 레거시 의존 졸업표

새 계통이 옛 계통의 **껍데기**가 되지 않게 하는 표다. 선은 *새 코드냐 옛 코드냐*가
아니라 **계산이냐 소유냐**로 긋는다.

> **계산과 실측값은 공유한다. 장치와 상태의 소유권은 ROS가 가진다.
> 웹 서비스에는 붙지 않는다.**

기구학을 ROS 쪽에 다시 쓰면 **같은 팔을 두 계통이 다르게 믿게** 된다 — 이 저장소가
반복해서 비싸게 배운 실패다. 그러니 순수 함수를 쓰는 건 "레거시를 따라가는 것"이
아니라 라이브러리를 쓰는 것이다(`math`·`numpy`를 쓰는 것과 같은 층).

| 무엇을 | 어디서 쓰나 | 판정 | 언제 끊나 |
|---|---|---|---|
| `kinematics` (import: `math`) | `arm_node` | **공유** | 안 끊는다 |
| `handeye` (import: `numpy`) | `handeye_node`, `detect_node` | **공유** | 안 끊는다 |
| `cartesian` (영점·환산·안전) | `arm_node`, `arm_source` | **공유** — 이 팔의 실측값은 한 벌 | 안 끊는다 |
| `eye.EyeConfig` (`~/arm_eye.json`) | `handeye_node` | **공유** — 이 카메라의 보정도 한 벌 | 안 끊는다 |
| `ports`, `servo_probe`, `config` | `follower_io` | **공유** — 유틸·상수 | 안 끊는다 |
| `motor_link` (주행 보드 드라이버) | `cmd_vel_node` | **과도기** | `v2.0.0-ros.4` — `ros2_control` 하드웨어 인터페이스로 승격 |
| `lerobot.SOFollower` (모터 버스) | `follower_io` | **과도기** — import 하나에 **torch 607MB**가 딸려온다(실측 3.5초) | `v2.0.0-ros.4` — `scservo_sdk` 직결. ⚠ 그때 정규화(-100..100) 규약을 lerobot과 똑같이 맞춰야 한다(안 그러면 영점의 뜻이 달라진다) |
| `arm.LerobotArm` | — | **금지** (ros.1에서 끊음) | 끝 |
| `voice.*` (웹 서비스) | — | **금지** | 끝 |
| `harvest.SceneModel` | — | **금지** — 새 계통이 없애려는 그것이다 | 끝 |
| `vision.*` | — | **금지** — 검출은 ROS 토픽으로 | 끝 |
| `arm_mode:=proxy` (HTTP) | 브링업 확인용 | **과도기** | `v2.0.0-ros.3` — 삭제 |

### 강제하는 방법

`ros2/tools/ros_selfcheck.py`의 **[경계]** 검사가 `ros2/src`의 모든 `tomato_picker.*`
import를 모아 이 표와 대조한다. 금지 목록에 걸리거나 **표에 없는 것이 나오면 실패**한다
— 새 의존을 들일 때 판정을 적게 만드는 것이 목적이다.

웹 서비스는 import가 아니라 HTTP로 붙으므로 같은 검사가 **기본값**을 본다:
`arm_mode`가 `direct`인지, 보정 경로가 비어 있는지(= `~/arm_eye.json` 한 벌인지).

### `proxy`가 왜 기본이면 안 되는가

이 계통을 만든 까닭 중 하나가 **시간**이었다(§ROS를 쓰는 이유 ②). 깊이 프레임과
관절값은 다른 시각의 데이터라 *그 프레임을 찍은 순간의* 팔 자세로 풀어야 한다.
`proxy`는 남의 프로세스에 10Hz로 물어본 값이라 "언제의 자세인가"가 흐릿하고,
대시보드가 바쁘면 `stale`까지 온다. 그 위에 TF를 그리면 팔이 실제와 다른 곳에
그려지고, 그 위에서 계산한 좌표가 **전부** 틀린다.

포트가 안 열린다고 `proxy`로 도망가지 말 것. 답은 `systemctl stop tomato-voice`다.

### ⚠ 장치는 셋 다 배타적이다

| 장치 | 레거시가 잡는 것 | ROS가 잡는 것 |
|---|---|---|
| `/dev/ttyACM0` (팔) | `tomato-voice.service` | `arm_node` (`direct`) |
| `/dev/ttyUSB0` (주행 보드) | `controller-drive.service` | `cmd_vel_node` |
| **D405** | `depth-cam.service` (`/dev/shm`) | `realsense2_camera` |

세 번째가 처음에 문서에 빠져 있었다. 팔·바퀴만 신경 쓰고 카메라를 안 껐다가
`realsense2_camera`가 조용히 못 여는 일이 생긴다.

### `v2.0.0` 통과 조건

**`tomato-voice`·`depth-cam`·`controller-drive`를 전부 끈 채로 1단계 전체가 돈다.**
그때 레거시 의존은 위 표의 "공유" 줄만 남는다 — 그건 라이브러리이지 계통이 아니다.

## 5. 다음에 할 일 (`ros.2`로 가는 길)

### ① 링크 길이와 마운트를 **자로 잰다**

`ros2/src/tomato_description/config/so101_geometry.yaml`의 값은 도면 근사치다.
FK와 IK가 같은 틀린 값을 쓰므로 조그는 방향만 맞고 크기가 어긋나며, **절대 좌표
이동은 그만큼 통째로 틀린다.**

재는 법은 [`kinematics.py`](../src/tomato_picker/hardware/kinematics.py)의
`ArmGeometry` docstring에 있다. 재고 나면 `ros_selfcheck.py`가 코드 기본값과의
불일치를 알려 주므로 **양쪽을 같이 고쳐야 한다**(그게 그 검사의 목적이다).

### ② 손-눈 보정을 실제로 한다

**지금 하드웨어는 `on_arm`이다** — D405가 5번 관절(wrist_roll) **뒤**, 집게 바로 위에
붙어 집게 앞을 본다. 컬러 화면 아래에 보이는 검은 덩어리가 그 집게다. 그래서
마커를 **책상에 고정**하고 팔 자세를 크게 바꿔가며 8회 이상 찍는다(집게에 붙이는
것은 `fixed`용이다). 차체 고정용 ORBBEC Astra Pro는 아직 안 왔다.

절차는 [`ros2/docker/README.md`](../ros2/docker/README.md) §3.
잔차 RMS 15mm는 **열매 지름이 30~40mm라서** 나온 숫자다 — 그보다 크면 집게가
헛집는다. 넘으면 표본을 더 넓게 흩어서 다시 찍어라.

#### 보정이 맞았는지 눈으로 거르는 법 — `camera_at`

`eye.py`의 스냅샷이 `camera_at`을 준다(`on_arm`이면 **집게 기준 카메라 위치**).
실물 배치(2026-08-31 사진)는 카메라가 집게 무는 지점에서 **뒤로 약 7~8cm,
위로 약 7~8cm**다. 풀린 값이 그 근처가 아니면 자릿수부터 틀린 것이다 —
잔차가 작아도 믿지 마라(표본이 한 뭉치에 몰리면 그럴 수 있다).

그 배치의 부수 효과 하나: **파지 순간에도 열매가 카메라에서 약 108mm**다
(스탠드오프 45mm면 143mm, 접근 시작 150mm면 238mm). 전부 D405 유효범위
70~500mm 안이다 — 손목 장착이라 거리가 자동으로 좋은 구간에 들어온다.
(`near_frac`이 낮게 나왔던 건 팔이 접혀 방을 보고 있었기 때문이지 배치 문제가
아니었다.)

#### ⚠ `on_arm`에서 두 계통의 "도구 좌표계"가 다르다 — wrist_roll을 고정하라

보정 파일은 한 벌이지만, `on_arm`에서 **그 값을 해석하는 방식이 서로 다르다.**

| | 도구 좌표계를 어떻게 만드나 | wrist_roll |
|---|---|---|
| 레거시 `eye.py` | `handeye.tool_frame(pose)` (`eye.py:339`, `:390`) | **무시한다** — `tool_axes`가 pitch·방위각만 쓴다 |
| ROS `handeye_node` | `tf2`로 `arm_base → tool0` 조회 | **포함한다** — URDF의 wrist_roll 관절이 들어 있다 |

카메라는 물리적으로 wrist_roll **뒤**에 붙어 있으므로 roll과 **같이 돈다.** 즉 TF
쪽이 물리적으로 옳고, `tool_frame()` 쪽은 roll이 보정 때와 다른 순간부터 틀린다.
(`tool_frame`의 docstring도 "손목 장착 보정 중에는 roll을 고정하라"고 적고 있다 —
그건 보정 중의 주의사항이지만, 같은 오차가 **운용 중에도** 그대로 나타난다.)

**지금 지킬 규칙:** 보정할 때와 열매를 집을 때 **wrist_roll을 같은 값으로 둔다.**
그러면 두 계통이 같은 답을 낸다.

**근본 해결:** `handeye.tool_frame()`이 roll을 포함하게 고치면 된다(`fixed` 경로는
`tool_frame`을 쓰지 않으므로 영향이 없다). 그건 D405 통합 작업이 소유한 파일이라
여기서 건드리지 않았다 — **그쪽과 맞춰서 한 번에 바꿔야 한다.**

### ③ duty 곡선 재기 (`duty_measured: true`로 가는 길)

지금 `Ks=90`은 실측이지만 `Kv`는 아니다. 그래서 `/cmd_vel`의 m/s는 **방향과
비율만** 맞다. 재는 법:

1. 바닥에 1m 눈금을 그린다(또는 라인 카메라의 픽셀 이동을 쓴다).
2. duty를 120, 150, 180, 210으로 두고 각각 **2초씩** 직진시켜 이동 거리를 잰다.
   (0.12초 펄스로 재지 말 것 — 가감속 구간이 절반을 차지한다.)
3. `속도[mm/s] = 거리 / 2`. duty를 x축, 속도를 y축에 놓고 직선을 맞춘다.
   기울기의 역수가 `Kv`(duty per mm/s), x절편이 `Ks`다.
4. 회전도 같은 방법으로(제자리 360° 도는 데 걸린 시간).
5. `stage1.yaml`에 넣고 `duty_measured: true`.

⚠ **배터리 전압에 따라 곡선이 움직인다.** 그게 보드계약 v2가 폐루프로 가려는
이유고, 그때까지는 "완충 직후에 잰 값"이라는 단서를 달아 두는 것이 정직하다.

### ④ 기존 무대 학습 걷어내기 (`v2.0.0`에서)

`harvest.py`의 `SceneModel`은 좌표가 생기면 **필요 없어진다** — 나무 번호도
높이도 3D 좌표에서 바로 나온다. 다만 걷어내는 순간 음성 명령("2번 나무 위쪽")이
같이 죽으므로, 좌표 → 사람 말 변환을 먼저 만들어 둔 뒤에 지운다.
