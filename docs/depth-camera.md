# 깊이 카메라 — 보정부터 통합까지

*2026-08-28: Intel RealSense D405 (시리얼 260322272920, FW 5.15.1.55, USB3.2).*
*2026-09-01: Orbbec Astra Pro (시리얼 17121112300, FW 5.8.22, USB2.0) 추가 — §9.*

## 카메라가 둘이다 — **어느 쪽이 더 좋은 게 아니라 쓰는 자리가 다르다**

| | D405 | Astra Pro |
|---|---|---|
| 유효 거리 | **7~50cm** | **60~400cm** (스펙 0.6~8m) |
| 쓰는 자리 | 집게가 열매를 무는 순간 | 무대 전체를 보는 삼각대·차체 |
| 깊이 원리 | 능동 IR 스테레오 | 구조광(IR 패턴) — 햇빛에 약하다 |
| 깊이 단위 | **0.1mm**/단위 | **1mm**/단위 |
| 컬러↔깊이 정렬 | ✅ (발행기가 depth→color 정렬) | ❌ RGB가 **별개의 USB 장치**다 |
| 발행기 | `tools/depth_cam.py` (pyrealsense2) | `tools/astra_cam.py` (OpenNI2) |
| 서비스 | `depth-cam` | `astra-cam` |
| /dev/shm | `d405_*` | `astra_*` |

D405를 처음 달았을 때 **삼각대가 무대에서 2m 떨어져 있어 장면의 0%가 유효범위
안이었다**(§0). 그 구멍이 Astra의 자리다. 반대로 Astra는 60cm 아래를 아예 못 본다 —
집는 순간의 거리는 D405만 볼 수 있다. **둘 다 있어야 한 바퀴가 돈다.**

읽는 코드(`hardware/depth_camera.py`)에는 카메라별 분기가 **없다**. 깊이 단위도
유효 거리도 정렬 여부도 전부 `meta.json`이 말해주고, 코드는 그걸 따른다.
`DepthView(camera="astra")` 처럼 이름만 다르다. 보정도 카메라마다 따로 저장된다
(`~/arm_eye.json` 안에서 칸이 나뉜다 — §9).

⚠ **둘을 한 프로세스가 잡지 않는다**(장치는 한 프로세스만). 서비스가 둘로 나뉜
이유도 그것이다. 대시보드 `/control`의 **[카메라]** 에서 골라 쓴다.

지금까지 팔은 **사람이 좌표를 말해줘야** 움직였다(`docs/arm-cartesian.md`).
D405는 그 좌표를 **카메라가 말하게** 한다 — 화면의 열매를 클릭하면 팔이 그 앞에 선다.

```
D405 픽셀 ─(깊이)→ 카메라 좌표 3D ─(손-눈 보정)→ 팔 base 좌표 ─(역기구학)→ 관절
   depth_camera.py        handeye.py                 cartesian.py / kinematics.py
                              └──────── eye.py 가 셋을 잇는다 ────────┘
```

## 0. 먼저 알아야 할 세 가지

**① D405는 근거리 전용이다.** 이상 동작범위 **7~50cm**. 1m를 넘으면 오차가 열매
지름(30~40mm)을 넘어 집기에 못 쓴다. 2026-08-28 첫 연결 때 삼각대가 무대에서 2m
떨어져 있었고, 장면의 **0%**가 유효범위 안이었다. 보정을 아무리 잘해도 소용없는
상태였다. 대시보드가 `유효범위 안이 N%` 로 이걸 계속 말해준다 — **그 숫자를 먼저 보라.**

**② 기구학 영점이 보정보다 먼저다.** 손-눈 보정은 "카메라가 본 집게 위치"와 "팔이
아는 집게 위치"를 짝지어 푼다. 영점이 없으면 뒤쪽에 뜻이 없어서 보정이 통째로
무의미하다. `/settings`의 **[3D 좌표 영점]**을 먼저 잡는다.

**③ 삼각대 고정은 바퀴가 움직이면 거짓이 된다.** 삼각대는 *지면*에 고정이지
*로봇*에 고정이 아니다. 로봇이 굴러가면 팔과 카메라의 관계가 바뀌는데 코드는 그걸
알 방법이 없고, 팔은 아무 일 없다는 듯 엉뚱한 데로 간다. **주행 후에는 다시 잡아라.**
손목/차체 장착으로 옮기면 사라지는 문제다.

## 1. 설치 (한 번만)

```bash
~/.venvs/vision/bin/pip install pyrealsense2      # aarch64/cp312 휠이 PyPI에 있다
sudo cp deploy/depth-cam.service /etc/systemd/system/
sudo cp deploy/50-tomato-services.rules /etc/polkit-1/rules.d/
sudo systemctl daemon-reload && sudo systemctl enable --now depth-cam
```

librealsense를 소스 빌드할 필요가 없다 — `pyrealsense2` 휠이 라이브러리를 품고 있고,
D405는 커널의 `uvcvideo`가 이미 잡는다(`server` 계정이 `video`·`plugdev` 그룹에 있어야 함).

확인:
```bash
systemctl is-active depth-cam
cat /dev/shm/d405_meta.json        # near_frac 이 "유효범위 안 비율"이다
```

## 2. 구조 — 왜 프로세스를 나눴나

카메라는 **vision venv의 `tools/depth_cam.py` 하나만** 잡고, /dev/shm으로 발행한다.
팔·음성 스택은 다른 venv(`~/lerobot/.venv`)라 pyrealsense2를 못 쓴다.
`tomato_vision.py`·`line_follow.py`와 같은 구조다.

| 파일 | 내용 |
|---|---|
| `/dev/shm/d405_color.jpg` | 컬러 프레임 (대시보드 `/video3`, 색검출) |
| `/dev/shm/d405_depth.npy` | 컬러 격자에 정렬된 uint16 깊이 (814KB) |
| `/dev/shm/d405_depth.jpg` | 깊이 컬러맵 (`/video4`) — **검정 = 측정 못 함** |
| `/dev/shm/d405_meta.json` | 내부파라미터·깊이단위·시각·거리분포 |

### 현장에서 확인한 함정 세 가지

⚠ **`depth_scale`이 0.0001 m/단위(0.1mm)다** — 흔한 1mm가 아니다. 1mm로 가정하면
모든 거리가 10배가 되고, 보정은 배율 0.1을 보고하며 팔은 열매 열 배 뒤를 집으러 간다.
그래서 이 값을 카메라에서 **읽어서** meta.json으로 넘긴다 — 코드에 상수로 박지 않는다.

⚠ **정렬은 depth→color 방향이어야 한다.** 반대로 하면 컬러가 깊이 격자로 워핑되면서
깊이가 무효인 픽셀마다 **컬러에 검은 구멍**이 뚫린다(실측 유효율 0.65 → 화면 1/3이
검은 얼룩). 색검출이 그 구멍을 경계로 오인한다. 이쪽 방향은 공짜였다(29.9fps).

⚠ **컬러와 깊이의 내부파라미터가 다르다.** depth는 정류돼 왜곡계수가 전부 0인데
color는 `inverse_brown_conrady`에 계수가 있다 — 무시하면 중심에서 먼 픽셀이 50cm에서
**8mm** 틀어진다. 컬러에 정렬했으므로 역투영도 컬러 쪽 파라미터를 쓴다.
(depth→color 외부파라미터는 회전≈단위행렬, 평행이동≈0.01mm. D405는 같은 스테레오
모듈에서 컬러와 깊이가 나오기 때문이다.)

### 노출·게인 — **센서가 하나다** (2026-09-18 추가)

⚠ **D405는 컬러·깊이·적외선이 한 센서(`Stereo Module`)에서 나온다.** 그래서
"컬러만 밝게"가 없다 — 노출과 게인이 **깊이에도 같이 걸린다**. 실측(조명 없는 무대):

| 설정 | 컬러 평균 | 99백분위 | 최댓값 | 깊이 유효율 | 근거리비율 |
|---|---|---|---|---|---|
| 자동노출(기본) | 7.6 | 17 | 48 | 0.093 | — |
| `exp=165000us · gain=248`(최대) | 34.8 | 66 | 115 | 0.542 | 0.959 |

여기서 배운 것 둘:
- **컬러는 손잡이를 끝까지 올려도 평균 34가 한계다.** 화면이 어두우면 먼저
  손잡이를 끝까지 돌려 보고, 그래도 안 되면 그건 **무대 조명 문제**다.
  (자동노출은 깊이 기준으로 맞추므로 컬러를 밝혀 주지 않는다.)
- **깊이 유효율은 5.8배가 된다.** 컬러를 포기해도 이 손잡이는 값을 한다.

손잡이 = `deploy/depth-cam.service`의 환경변수. 지금은 **켜져 있다**.

```
Environment=D405_EXPOSURE_US=165000     # us. 주면 자동노출은 꺼진다
Environment=D405_GAIN=248               # 16~248
Environment=D405_AUTO_EXPOSURE=0        # 수동값 없이 자동만 끄고 싶을 때
```

⚠ 165ms 노출은 스트림을 **6.0fps**로 떨어뜨리고 움직이는 것을 흐리게 만든다
(2026-09-18 실측, 아래 §2.1). 팔·베이스를 움직이며 컬러를 보려면 위 두 줄을 지워라.
⚠ `D405_AUTO_EXPOSURE=1`과 수동값을 같이 주면 **거절한다** — 자동노출이 곧바로
덮어써서 "지령은 나갔는데 아무 일도 안 일어나는" 모양이 되기 때문이다.

⚠ **화면 밝기는 meta.json이 말한다** — `color_mean`·`color_p99`·`color_max`와
실제로 걸린 `exposure`/`gain`/`auto_exposure`가 실린다. `DepthView.status()`는
99백분위가 30 아래면 `color_warn`을 단다: 점 검출(`target_check.find_dots`)이
밝기 차 30을 요구하므로, 그보다 어두우면 **검출 0개는 "표적이 없다"의 증거가
아니다.** 2026-09-17에 이 구분을 못 해 하루를 썼다
(→ [`인수인계-2026-09-04.md`](인수인계-2026-09-04.md) §21.7·§21.9).

### 2.1 발행 주기 — **"신선하다"와 "제때 온다"는 다른 질문이다** (2026-09-18 추가)

`D405_PUBLISH_FPS`는 **바라는** 값이지 나오는 값이 아니다. 노출을 165ms로 올린
뒤 실제로 나오는 것은 **6.0fps**다(설정 8의 75%). 그런데 읽는 쪽이 보던 것은
`age`(프레임 나이)뿐이었고, 6fps여도 age는 0.17초라 **굳음 검사를 멀쩡히
통과한다.** 그 0.17초 사이에 팔이 움직였으면 겨눈 화소는 이미 남의 자리다
(→ [`개발일지-2026-09-11.md`](개발일지-2026-09-11.md) §1 "겨냥이 정확할수록 틀린
자리로 정확히 간다"). 이 저장소의 1번 병이 프레임 주기에서 재발하는 자리다.

그래서 **깊이 단위·유효 거리와 같은 규칙** — 카메라가 스스로 말한다.
meta.json에 세 값이 실린다(두 발행기 공통):

| 키 | 뜻 |
|---|---|
| `capture_fps` | 스트림을 연 fps (`D405_FPS`, 기본 30) |
| `publish_fps` | 파일로 내보내려는 목표 (`D405_PUBLISH_FPS`, 기본 8) |
| `measured_fps` | **실측** — 최근 `D405_FPS_WINDOW_SEC`(기본 4초) 창의 간격 수 ÷ 걸린 시간. 표본이 모자라면 `null`("0"이 아니라 "아직 모른다") |

판정은 **읽는 쪽**이 한다(발행기는 임계를 안 박는다) —
`config.D405_MIN_FPS_FRAC`(0.8)보다 느리면 `DepthView.status()`가 `fps_warn`을,
조작대(`http://<젯슨IP>:8090/`)가 프레임 줄에 `⚠ 6.0fps (설정 8.0)`를 단다.

실측 2026-09-18 (노출 165ms·gain 248):

| | 설정 | 실측 | 비고 |
|---|---|---|---|
| D405 | 8.0 | **6.0** | seq 6097→6157 / 9.99초로도 같은 값. 노출 165ms = 6.06fps가 상한 |
| Astra | 8.0 | 7.42 | 노출을 안 건드려 목표에 가깝다(경고 안 뜸) |

### 2.1.1 그래서 거절하는가 — 한다, 단 **겨냥에만** (T25, 2026-09-18)

경고만으로는 아무도 안 멈춘다. 그래서 **화소로 팔을 보내는 길**(`Eye.pixel_to_base`
→ `aim`)에는 굳음 한계(2초)와 별개로 좁은 한계를 두고 **거절한다** —
`config.D405_AIM_MAX_AGE_SEC`(0.35초). 부르는 쪽이 `point_at(..., aiming=True)`로
"이 값으로 팔을 보낸다"고 선언할 때만 좁아진다. 거리만 재는 길(`probe`)과 열매
목록은 그대로다 — 보기만 하는 것까지 막으면 화면이 통째로 죽는다.
`DepthView`는 팔이 움직였는지 알 수 없다. 아는 것은 부르는 쪽이다.

⚠ **한계의 단위를 '프레임 수'로 잡으면 안 된다.** "2프레임"으로 적으면 6fps에서
0.33초, 3fps에서 0.67초 — **느려질수록 관문이 넓어져** 막으려던 바로 그 상황에서
문이 열린다. 그래서 절대 시간으로 자른다. `eye_check`의 [겨냥]에 이 실수가
회귀하면 걸리는 검사를 넣어 뒀다(0.5초 낡은 프레임 + 실측 3fps).

fps는 대신 다른 몫을 한다 — 주기(1/fps)가 한계보다 길면 **어떤 프레임도** 통과할
수 없다. 그건 "가끔 실패"가 아니라 막다른 골목이므로, `status()`의 `aim_warn`과
조작대 프레임 줄의 `⛔ 겨냥 불가`가 원인(노출)과 함께 미리 말한다. 지금 구성
(6.0fps = 주기 167ms)은 한계 350ms 안이라 겨냥이 막히지 않는다. 2.9fps 아래로
떨어지면 막힌다.

⚠ **0.35초의 보수성 — 기하 상한 검산 (2026-09-18, T48)**

직접 실측(T48 원래 완료조건)은 실기 세션이 필요해 아직 미완이다.
대신 두 경로로 **불가능한 값을 거를 수 있는지** 확인한다.

**경로 1 — 기하 상한**: STS3215 서보 최대 속도 약 6.2deg/s, 가장 긴 팔 구간 l2+l3=295.5mm
TCP 최대 속도 약 295.5 x 0.108 rad/s = **32 mm/s**.
허용오차 15mm / 32mm/s = **0.47초**가 물리적 상한이다.
0.35초는 이보다 짧으므로 서보 최대속도 기준으로는 충분히 보수적이다.

**경로 2 — 기록 역산(짐작)**: 2026-09-18 07:04 연속 5판의 타임스탬프와 TCP 도달 좌표로
3쌍을 역산했다. settle 라운드 포함 평균 **22mm/s**, 최대 28mm/s.
0.35초 동안 이동량 약 7.8mm → 15mm 이내. (주: 타임스탬프가 settle 완료 시각이라
실제 이동 속도는 더 높다 — 실측 필요)

**aim_age의 진짜 위험 구간**: 팔이 이동 중일 때는 age가 계속 쌓여 aim이 거절된다.
실제 위험은 클릭 → `pixel_to_base` 호출 사이 지연(수십 ms 수준)이다.
코드 근거: `config.py:750`, `depth_camera.py:140`.

**결론(검산됨, 실측 부족)**: 현재 0.35초는 물리 상한(0.47초)보다 짧아 보수적이다.
실기 조그·이동 중 실측 속도가 아직 없으므로 T48은 열어 둔다.
실측 결과가 나오면 이 절을 덮어쓴다.

팔이 이동·조그 중 초당 몇 mm 가는지를 재면 "허용 오차 15mm / 속도"로 이 숫자가
정해진다 — 그 실측이 이 절에 들어올 자리다(T48).

조작대(`~/click_target.json`)에는 표적을 찍은 **프레임의 ts**(`frame_ts`)와 클릭
시각(`ts`)이 함께 남는다. 표적 화소는 그 프레임의 자리이고, 팔이 움직이면
무효가 되기 때문이다(개발일지-2026-09-11 §1).

## 3. 보정 절차 — 삼각대·차체 고정 (`fixed`)

미지수는 강체 변환 하나(6개). **집게(TCP) 자체를 마커로 삼는다.**

1. `/settings` → **[3D 좌표 영점]** 을 먼저 잡는다 (안 잡혀 있으면 아래가 막힌다).
2. `/settings` → **카메라 3D 보정** → 장착 방식 **[삼각대·차체 고정]**.
3. `/control` → **깊이 카메라 D405** 패널. 클릭 모드 **[거리만 재기]** 로 먼저
   무대를 찍어 보고, **거리가 7~50cm 안**인지 확인한다. 아니면 삼각대를 당긴다.
4. 클릭 모드를 **[보정 표본 담기]** 로 바꾼다.
5. 팔을 카메라가 보는 자리로 옮기고(프리셋·조그 무엇이든), 화면에서
   **집게가 무는 지점**을 클릭한다 → 표본 1개.
6. 팔을 **멀찍이** 옮겨가며 5번 이상 반복. ⚠ 좌우·상하·앞뒤로 **크게** 흩어라.
   한 뭉치에 몰리면 회전이 결정되지 않는다(코드가 한 직선이면 거절한다).
7. **[보정 풀기]** → 잔차(RMS)를 본다.

### 잔차 읽는 법 — **이걸 안 보면 보정을 한 게 아니다**

최소자승은 입력이 쓰레기여도 답을 내놓는다. 맞았는지는 오직 잔차가 말한다.

| 잔차 | 뜻 |
|---|---|
| ~5mm 이하 | 좋다. 그대로 쓴다. |
| 15mm 초과 | **팔을 보내지 마라** (집게가 헛집는다). 코드가 `aim`을 막는다. |
| 특정 표본만 크다 | 잘못 클릭한 것. 그 번호만 지우고 다시 푼다(메시지가 번호를 알려준다). |
| **배율 경고** | 깊이 단위나 링크 길이(`ARM_GEOM_L*`)가 틀렸다. 게인이 아니라 **단위**를 의심하라. |

카메라 위치(`camera_at`)도 화면에 뜬다 — 삼각대가 팔 앞 40cm에 있다면 그 정도
숫자여야 한다. **자릿수가 다르면 뭔가 틀린 것이다.**

## 4. 보정 절차 — 손목 장착 (`on_arm`)

카메라가 팔과 함께 움직이므로 미지수가 다르다: `T_tool_cam`(6) + 고정 마커 위치(3) = 9.

1. 마커(빨간 공 하나면 된다)를 **한 자리에 고정**한다.
2. 장착 방식을 **[손목 장착]** 으로 바꾼다(기존 보정은 버려진다 — 뜻이 달라지므로).
3. 팔 자세를 **크게 바꿔가며** 그 마커를 **8번 이상** 클릭한다.
   ⚠ 같은 방향에서 거리만 바꾼 표본은 아무리 많아도 회전을 결정하지 못한다(거절된다).
   ⚠ **`wrist_roll`은 고정하라** — `tool_frame`이 roll을 쓰지 않으므로 돌리면 잔차로 남는다.
4. **[보정 풀기]**.

## 5. 쓰기

`/control`의 클릭 모드:

| 모드 | 하는 일 |
|---|---|
| 거리만 재기 | 그 픽셀의 거리·좌표만 알려준다. **팔을 안 건드린다.** 보정 전에도 된다. |
| 보정 표본 담기 | 표본 1개 추가 |
| 그 앞으로 팔 보내기 | 열매 앞 `ARM_EYE_STANDOFF_MM`(45mm)에 선다 |

**[🍅 보이는 열매 좌표]** 는 컬러에서 빨간 열매를 찾아 3D 좌표를 붙여 나열한다.
깊이가 안 나오는 열매는 버리지 않고 **왜 없는지**를 달아 남긴다.

집는 것까지 하려면: `aim` 으로 앞에 선 뒤 → 집게 열기 → `/control`의 **집게 기준**
조그로 `찔러넣기 ▶` → 집게 닫기. (자동 파지는 아직 없다.)

## 6. 거절되는 경우와 뜻

이 층은 **못 믿을 때 값을 주지 않는다.** 대충 된 값을 주는 쪽이 훨씬 비싸기 때문이다
(CLAUDE.md의 1번 병 "지령은 나갔는데 아무 일도 안 일어난다"의 비전판 = "엉뚱한
깊이를 받아 팔이 허공을 집는다").

| 메시지 | 원인 · 조치 |
|---|---|
| 깊이가 비어 있다 | 그 자리에 깊이 구멍(반사·그림자·7cm 미만). 다른 지점을 찍거나 조명을 보라 |
| 너무 멀다 (>900mm) | 삼각대가 무대에서 멀다. **당겨라** |
| 너무 가깝다 (<70mm) | D405가 측정하지 못하는 거리 |
| 프레임이 N초 전 것이다 | `depth-cam`이 죽었다. 굳은 화면으로는 팔을 안 움직인다 |
| 기구학 영점이 없습니다 | `/settings` → [3D 좌표 영점] |
| 잔차가 N mm입니다 | 표본을 더 흩어 다시 잡아라 |
| 한 직선 위에 있다 | 표본이 한 줄로 몰렸다. 좌우·상하·앞뒤로 흩어라 |

## 7. 자체검증 — 하드웨어 없이

```bash
python tools/handeye_check.py    # 보정 수식 63개 (numpy만)
python tools/eye_check.py        # 보정→통합 배선 60개 (가짜 깊이 파일로, 카메라 둘 포함)
python tools/arm_cartesian_check.py
python tools/pages_check.py      # 대시보드 JS가 살아 있는가
```

⚠ `pages_check.py`를 왜 만들었나 — 2026-08-28, `/settings`의 스크립트가 **파싱
실패로 통째로 죽어 있었다.** 파이썬 문자열 안의 `\n` 하나가 진짜 줄바꿈이 되어
JS 문자열을 끊은 것이다. 증상이 조용했다: 페이지는 멀쩡히 뜨고, **버튼만 아무
반응이 없고**, 상태는 "확인 중..."에 멈춰 있었다. 그 바람에 **팔 영점을 한 번도
못 잡았고**, 그 위에 얹힌 손-눈 보정은 시작조차 못 하고 있었다.

`handeye_check`는 **정답을 심어 놓고 되찾아오게** 한다. `eye_check`는 가짜 깊이
프레임을 진짜 파일로 구워 `DepthView`·`EyeCalibrator`·`Eye`·`CartesianArm`을 그대로
통과시킨다. "팔이 열매 옆 5cm를 집는다"의 원인 후보(카메라·보정·기구학·영점) 중
셋을 여기서 미리 지운다 — 현장에서 가르기 가장 어려운 종류다.

해상도를 바꾸면 내부파라미터가 달라지는데, 그 기록이 없으면 왜 빗나가는지 아무도 모른다.

⚠ **팔 범위 캘리브레이션을 다시 하면 영점도 보정도 다시** 잡아야 한다
(정규화값의 뜻이 바뀌므로).

## 9. Orbbec Astra Pro (2026-09-01 추가)

### 왜 달았나

D405로는 **무대를 볼 수 없다.** 삼각대에서 무대까지가 1~2m인데 D405의 유효
거리는 50cm까지다. Astra Pro는 60~400cm를 본다 — 정확히 그 구멍이다.

### 설치 — 한 줄

```bash
bash deploy/astra-install.sh
```

⚠ **apt로는 안 된다.** 우분투의 `libopenni2-0`이 들고 있는 PS1080 드라이버는
PrimeSense VID(`0x1d27`)만 찾는다. Orbbec은 `0x2bc5`라 **장치가 하나도 안 잡히는데,
에러가 아니라 "장치 0개"로 조용히 끝난다.** 카메라가 고장난 것처럼 보인다.
스크립트가 Orbbec 재배포본(`liborbbec.so` + 같이 빌드된 `libOpenNI2.so`)을
`~/openni2`에 풀고, udev 규칙과 서비스를 넣는다.

스크립트가 하는 일:

| | 무엇 | 왜 |
|---|---|---|
| ① | Orbbec OpenNI2 arm64 런타임 → `~/openni2` | apt 드라이버가 Orbbec을 못 본다 |
| ② | `orbbec.ini`의 `[Depth]`를 **640x480@30**으로 | 기본값 640x400은 프레임이 깨진다(아래) |
| ③ | `56-orbbec-usb.rules` | USB 장치를 `video` 그룹에 연다 |
| ④ | `astra-cam.service` enable | 부팅 자동 실행 |
| ⑤ | `/dev/shm/astra_meta.json` 확인 | 숫자를 눈으로 본다 |

### 현장에서 실제로 확인한 것 (실측 2026-09-01)

⚠ **ini 기본 해상도(640x400)로 열면 매 프레임이 깨진다.**
`Depth buffer is corrupt. Size is 511856 (!= 512000)` — 정확히 **144바이트**가
모자란다. 640x480(`Resolution=1`)으로 바꾸면 멀쩡하다. USB 대역 문제가
**아니었다** — `usbfs_memory_mb`를 16→1000으로 올려도 그대로였고, ISO 엔드포인트
(`UsbInterface=1`)는 이 장치에 아예 없다(벌크 0x81/0x82뿐). 해상도 하나였다.

⚠ **깊이가 전부 0인데 카메라는 정상일 수 있다.** 첫 연결 때 벽에서 20cm 앞에
놓여 있었고 유효 픽셀이 **0%**였다. 60cm보다 가까우면 측정이 안 되고, LDP(레이저
보호)가 아예 투광기를 끈다. 대시보드가 `유효범위 안 N%`와 중앙값을 말해준다 —
**그 숫자를 먼저 보라.** D405의 "너무 멀다"와 정확히 대칭인 병이다.

⚠ **그리고 그 0%는 카메라를 옮겨도 저절로 안 풀린다** (2026-09-02 실측, 이게 진짜 함정).
카메라를 방 쪽(0.6~2.2m)으로 돌려놨는데도 발행기는 계속 **0%**를 냈다. 그런데 같은
자리에서 프로세스를 새로 띄우자 즉시 **79%**가 나왔다. LDP가 끈 투광기가 **스트림
수명 내내 꺼진 채 유지되는** 것이다. `LASER_EN=1`·`LDP_EN=0`을 넣어 봐도 달라지지
않았다(네 조합 모두 같은 값) — **장치를 다시 여는 것 말고는 방법이 없다.**

증상은 "카메라 고장"이고 원인은 "30분 전에 벽에 붙여 놨던 것"이라 사람이 이 둘을
잇기가 거의 불가능하다. 그래서 코드가 잇는다 — 프레임은 오는데 유효 픽셀이
`ASTRA_ZERO_REOPEN_SEC`(기본 30초) 동안 하나도 없으면 발행기가 **스스로 끝나고**
systemd가 새로 띄운다. 로그에 왜 그랬는지 남는다. 렌즈가 막혔거나 정말로 가까운
것만 보고 있으면 다시 열어도 같으므로, **그 줄이 반복되면 카메라가 보는 곳을 보라.**

실측 (방 안, 문 0.6m ~ 안쪽 벽 2.2m):

| | 값 |
|---|---|
| 유효 픽셀 | 78% |
| 유효범위(60~250cm) 안 | **96%** |
| 거리 중앙값 | 1451mm |
| p05 / p95 | 603 / 2225mm |

⚠ **컬러는 깊이와 정렬돼 있지 않다.** Astra Pro의 RGB는 별개의 USB 장치(UVC,
`/dev/video0`)라 하드웨어 동기도 정렬도 없다. 게다가 이 개체는 공장 D2C
보정값(`OBCameraParams`)이 **전부 NaN**이다 — 소프트웨어로 맞출 근거조차 없다.
그래서 `meta.json`에 `color_aligned: false`를 싣고, **컬러 픽셀 클릭을 거절**한다.
Astra를 고르면 화면이 깊이 뷰로 넘어가고 컬러 라디오가 잠긴다.
보정 클릭은 **깊이 화면**에서 한다(그쪽은 정의상 정렬돼 있다).

⚠ **내부파라미터는 화각에서 만든 것이다.** D405는 카메라가 `fx·fy·주점`을 직접
알려주지만 Astra는 **화각만** 준다(hfov 58.6° / vfov 45.6° → fx=fy=570.3).
주점은 화면 정중앙으로 **가정**한다. 실제 주점이 몇 픽셀 어긋나 있으면 그 오차는
손-눈 보정 잔차로 나타난다 — 잔차가 유난히 크면 이 가정을 먼저 의심하라.

⚠ **드라이버가 특정 호출에서 힙을 깨고 죽는다.** IR 스트림 생성,
`getProperty(IMAGE_REGISTRATION)`, `getProperty(LASER_EN)` — 전부
`malloc(): invalid size`로 프로세스가 죽는다. pip의 `openni` 바인딩으로 스트림을
만들어도 같다. 그래서 `astra_cam.py`는 **검증된 호출만** ctypes로 직접 부른다
(스트림 생성·모드 설정·읽기, 시리얼/장치이름 읽기). 편의로 호출을 하나 더
넣고 싶어지면, 그게 30분 뒤 서비스를 죽인다는 걸 기억하라.

⚠ **Astra의 RGB가 무대 카메라를 조용히 밀어냈다.** `tomato_vision.py`는
`/dev/v4l/by-id/`의 **첫 줄**을 웹캠으로 삼았는데, Astra를 꽂자 그 첫 줄이
바뀌었다(A < I). 서비스는 아무 말 없이 다른 카메라로 갈아탔고 에러는 하나도
안 났다. 지금은 깊이 카메라의 RGB 노드를 **뒤로 미루고**, 무엇을 골랐는지
로그에 찍는다. 고정하려면 `TV_CAMERA_DEV`.

### 보정 — D405와 같은 절차, 단 거리가 다르다

§3(삼각대 고정)·§4(손목 장착)와 절차가 같다. 다른 점만:

1. `/control`의 **[카메라]** 에서 **Astra**를 고른다 (화면이 깊이 뷰로 바뀐다).
2. **팔이 카메라에서 60cm보다 멀어야 표본이 담긴다.** 가까우면 "너무 가깝다"로
   거절된다 — 팔이 안 보이는 게 아니라 **이 카메라가 그 거리를 못 재는** 것이다.
3. 집게는 깊이 화면에서 **덩어리**로 보인다(컬러가 아니다). 무는 지점을 찍기가
   D405보다 어려우니, 팔을 배경에서 떼어 놓고 찍어라.
4. **보정은 카메라마다 따로 저장된다** — Astra를 잡아도 D405 보정은 그대로다.
   (`~/arm_eye.json` 최상위 = D405, `cameras.astra` = Astra. 최상위를 그대로 둔
   이유는 옛 파일과 ROS 쪽(`tomato_handeye/store.py`)이 그 자리를 읽기 때문이다.)

### 아직 안 된 것

- **ROS 2 계통엔 안 붙였다.** `ros2/`는 `realsense2_camera` 노드로 D405를 연다.
  Astra는 ROS 드라이버가 따로 필요하다(`ros_astra_camera`를 ROS 2로 빌드).
  지금 붙은 것은 **기존 스택(`src/tomato_picker/`)뿐**이다.
- **컬러↔깊이 정렬.** 공장값이 NaN이라 하려면 직접 재야 한다(체스보드로
